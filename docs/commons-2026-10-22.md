# tend commons: sessions that find each other and share what they know

Status: concept, no code. Proposed 2026-10-22; owner decisions in §8. It extends fleet awareness (F1), shared learning (F2), and fleet messaging (F4), and it widens them from fleets to every tend session.

## 1. The idea in one paragraph

Today a tend session knows about other sessions in two narrow ways. It notices their edits and git commands (F1), and it inherits the fixes they learned (F2). Only sessions inside a fleet can talk, and only along the channels a fleet file declares. The idea: **every session started through tend joins one local commons.** In it, each session has an identity: who it is, where it works, what it is doing, and how that is going. Any session can find the others, ask them, tell them, and publish what it learned for them to read. Agents then organize themselves around the work: they find who owns a file, avoid duplicate work, ask the session that already solved a problem, and hand over when they stop. tend gives them identity, a directory, and a channel. It never assigns them work.

## 2. Core principles

1. **Every tend session is a member.** No fleet file is needed. A fleet is a commons with a structure the user wrote down; an ad-hoc set of terminals is a commons without one.
2. **Identity is a card, kept true by tend.** A session's card says who it is (a name, the agent, the repo, the worktree), what it is doing (its task, in one line), and how it is going (working, blocked, waiting, idle, done). tend fills what it can observe: repo, files touched, last test result, loop or block state. The agent fills its intent. A card the agent writes can be wrong; a card tend observes cannot be faked.
3. **Pull by default, push by address.** Knowledge is published and read on demand: a session asks when it needs to. Only messages addressed to a session (by name, by file, by topic it joined) are pushed into its context. Nobody's context fills up with everybody's chatter.
4. **tend carries, agents decide, the user rules.** tend never plans, assigns, or merges. Agents choose whom to ask and what to share. The user sees everything, can stop any of it, and is the only one who can approve what persists or grants rights.
5. **Words are data, not orders.** Everything another session says reaches an agent labelled as another session's words, with its source. A message can never grant a permission, lift a guard, or change a role (the same rule as F4 and S6).
6. **Everything is on the record.** Every card change, message, publish, and read is a ledger entry with its cause, so `tend why` can follow a decision across sessions.
7. **Local and private.** One machine, one user, Unix sockets, 0700 directories. Nothing leaves the machine. Code stays in its project unless the user says otherwise (the 2026-10-22 decision for learned diffs).
8. **Cheap or silent.** If the commons is down or slow, a session works as it does today (fail open). Joining costs no tokens until a session asks or is addressed.

## 3. Who uses it, and for what

| # | Scene | Today | With the commons |
|---|---|---|---|
| U1 | Two terminals on polaris: one refactors `connectors/dartsim.py`, one writes a benchmark that calls it. | They learn of each other only when an edit lands (F1 notice). | Before it changes the call, B asks "who is working on dartsim?" and finds A's card: "refactoring the DartSim connector's action API". B asks A whether the signature will change; A answers at its next turn. |
| U2 | A new session is about to fix a failing test. | It may be the second agent fixing the same test. | Its start shows two cards in the same repo; one says "fixing test_certified_strategy failures, 10 min in". It works on something else, or offers help. |
| U3 | A session in tend-rs hits a pytest asyncio error. | It debugs from scratch. | It asks the commons. A polaris session that set `asyncio_mode = auto` last week published that finding; the answer comes from the published finding, without waking anyone. |
| U4 | You stop for the day mid-refactor. | Tomorrow's session reads git and guesses. | The session's last card ("done: X; open: Y; next: Z") stays in the commons. Tomorrow's session in that repo pulls it at start, like a project note, but specific to the work in flight. |
| U5 | You run four agents across three projects. | You switch terminals to see what each does. | `tend sessions` is one board: each card's task, status, last test result, what it waits for, and its unread messages. You message any of them from your terminal. |
| U6 | A session finishes a change that needs a review. | You copy its summary into another terminal. | It posts "review wanted: diff of 3 files in polaris" to the review topic. A session that declared it reviews (or you) takes it. Nobody was assigned; the work found a taker. |
| U7 | A library session changes an API that a consumer project uses. | The consumer breaks later. | The library session publishes "changed X's signature". A session whose card says it works on the consumer, and that subscribed to that library, gets it at its next hook. |
| U8 | One agent is stuck in a loop. | Only you can tell, if you look. | Its card says "loop on test_x, 4 attempts". A peer that fixed that signature before is told it could help; you see it on the board. |

## 4. The concepts

- **Card (identity and status).** One per session. Fields: name (unique on the machine, the agent may pick one, tend makes one otherwise), agent, repo and worktree, task (one line, by the agent), status (observed: working, blocked, waiting for an answer, idle, done; plus the agent's own word), files it touched lately (observed), last check or test result (observed), what it offers (for example `review`, `knows:pytest-asyncio`), and when it was last seen.
- **Directory (discovery).** Find cards by repo, file, topic, status, or what they offer. "Who is in this repo?", "who touched this file today?", "who reviews?".
- **Messages (push).** To a name, to the sessions in a repo, to a file's recent editors, or to a topic. Kinds as in F4: question, answer, notice, request, handoff. Delivered at the receiver's next hook, or as a turn to an idle headless session.
- **Topics.** Named channels sessions join ("review", "polaris-api"). Joining is how a session opts in to pushes it did not ask for.
- **Findings (knowledge, pull).** Short published facts: a fix (F2's learned fixes are one kind), a decision, a gotcha, a handoff card. They are read on demand ("anything about asyncio_mode?") or pulled at start for the same repo. Agents may publish; what persists past the session is the user's call (as notes are today).
- **Board (the user's view).** All cards, messages, and findings, live, with history in the ledgers.

## 5. What it must not become

- Not a chat room. Messages are short, typed, addressed, rate-limited, and recorded.
- Not a planner. tend shows who does what; it never decides who should.
- Not a way around permissions. A session cannot make another one run a command, edit a file, or lift a guard.
- Not a network service. Machine-local only.
- Not a cost sink. A session that never asks and is never addressed spends no tokens on the commons.

## 6. What tend already has, and what is missing

| Need | Today | Gap |
|---|---|---|
| Who else is running | Each daemon tails live ledgers (F1); `tend fleet` lists live sessions | No card: no name, task, or status beyond what edits show |
| Talking | `tend msg` inside a fleet, routed by the hub (F4) | Sessions outside a fleet cannot address each other; no topics |
| Delivery | Next hook as context; a turn for idle headless sessions (F4) | Works as is; reuse |
| Shared knowledge | Learned fixes, approved notes (F2) | No general findings; no query; no handoff card |
| Trust and record | Untrusted labels, ledger causes, deny of forged verbs | Extend to the new verbs |
| User view | `tend fleet`, `tend report`, inbox | One board for all sessions |

## 7. Risks

| Risk | Effect | Mitigation |
|---|---|---|
| Prompt injection spreads | A session that read a poisoned page talks to one with more rights. | Words are data (principle 5); no verb grants rights; rate limits; persistence needs the user. |
| Context noise | Pushed messages cost tokens and distract. | Pull by default; push only by address or joined topic; one digest per hook; per-session caps. |
| Stale or false cards | Agents trust a card that lies or is old. | Observed fields are tend's; agent-written fields are labelled; cards age out with the session. |
| Cross-project leakage | Code or secrets reach another project's session. | Findings carry their project; code stays in its project by default; redaction as for outputs. |
| Agents talk instead of working | Ping-pong between sessions. | Rate limits per pair; a waiting session is not woken by chatter; the board shows talk volume. |

## 8. Owner decisions (2026-10-22)

1. **Default: member, look.** Every tend session gets a card and can be found. `commons = off | look | on` (default `look`, like `fleet` and `learn`): look records what would be delivered; on delivers.
2. **Reach: cards everywhere, findings without code.** Any session sees every card on the machine. Findings cross projects as text; diffs and code stay in their project (as for learned diffs).
3. **Waking: only headless sessions, rate-limited.** An idle headless session gets an addressed question as a turn, capped per hour. A terminal session sees it at its next hook.
4. **Persistence: findings persist, labelled as an agent's.** Like learned fixes: kept, readable, marked as an agent's, droppable by the user. Notes stay the user-approved channel.
5. Open: whether a fleet's sessions see the wider commons or stay sealed.

## 8a. Questions that were put to the owner

1. **Default.** Is every tend session a member by default (with `commons = off | look | on`, like `fleet` and `learn`), or opt-in per session?
2. **Reach across projects.** May a session in one repo read another repo's cards and findings? Cards only, findings without code, or everything?
3. **Waking.** May one session wake another's idle headless session with a message (a new turn costs tokens), or must it wait for that session's next own activity?
4. **Persistence.** Do agent-published findings persist past the session without your approval (like learned fixes), or wait for review (like notes)?
5. **Fleets.** Should a fleet's hub become a member that relays (fleet sessions see the commons too), or stay sealed?

## 9. Shape of a build (after the questions)

Only a sketch, to show it fits. C1: cards, observed by each daemon, and `tend sessions`. C2: `tend msg` and topics for every session (a machine-level relay, or the hub code without a fleet). C3: findings and `tend ask` (pull). C4: handoff cards at session end. Each phase with a look mode first and a measurement gate, as for F1–F5.
