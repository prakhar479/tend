# tend fleet: sessions that know about each other

**Status:** design, approved by the owner 2026-10-21. Tasks F1–F6 are in `docs/TASKS.md` (Fleet F). Nothing is built yet. Topologies and fleet management are designed in full in `docs/fleet-topologies-2026-10-21.md`; it replaces F3 and F5 below.

## Context

Today each `tend claude` session has its own daemon, ledger, and session model. Each one is blind to the others. People already run several agents on one machine at once: parallel worktrees, a "fixer" and a "reviewer", a long auto-mode run plus an interactive one, and later Claude Code next to Codex. These agents step on each other, solve the same problem twice, and cannot hand work over.

tend sits at the right place to fix this. It sees every tool call of every session it supervises, in one vocabulary shared across agents (`event.rs`). It already has the pieces a fleet needs: error signatures that match the same failure across different text, a ledger with causes, capability-honest delivery (`inject_context`, `continue_turn`), and per-project memory (E9).

The owner's idea: let sessions on one machine talk to each other across providers, learn from each other, and organize into a topology the user picks (peers, leader and workers, pipeline, or custom).

## 0. Owner decisions (2026-10-21)

- **North star: awareness and learning.** These layers get the deepest design and are built first.
- **Spawning is a core feature.** tend may start and manage agent sessions (`tend fleet spawn`). It still does not plan work: an agent or the user decides what to spawn.
- **Setups to support:** same checkout, git worktrees, and different repos.
- **Build F1 now.** This overrides the 2026-10-20 feature gate for fleet. The F0 measurement still runs, as F1's first step, but it does not block F1.

## 1. The feature, from the user's side

### 1.1 Who uses it, and for what

| Scene | Today | With fleet |
|---|---|---|
| Two sessions in one checkout (or two worktrees that merge later) | B edits `api.rs` after A read it. A works from a stale view and overwrites B. | A's next hook says: "Session B (codex) edited src/api.rs 40 s ago, after you read it. Re-read before you edit." |
| One session spends 25 min in a loop on `ImportError: cannot import name X` | The next session on the same repo hits it and loops again. | On the second failure with the same signature, tend tells the new session: "This failure was fixed in session 7f3a by editing pyproject.toml (diff: `tend show f-12`)." |
| Long auto-mode run plus the user's interactive session | The user has no picture of the run. | `tend fleet` shows every live session: agent, repo, task, last tool call, loop or block state, files held. |
| Implementer, then reviewer | The user copies a summary from one terminal to the other. | When A stops, its summary and diff go to B's inbox. B starts from that. |
| Leader and workers | The user is the leader and splits tasks by hand. | A leader session posts tasks. Workers claim them, report back, and are told when a task they depend on is done. |
| Two sessions both run `cargo build` or bind port 8000 | They fight over the target dir lock or the port. | tend sees the second command start while the first runs and notes it (look) or tells the agent (optimize). |

### 1.2 Capabilities, in four layers

Each layer works without the ones above it. A user can stop at any layer.

**L1. Awareness (passive, no agent change).**
- A fleet view: `tend fleet` (live), plus a "fleet" section in `tend report`.
- Conflict detection from tool events alone: stale read (B wrote a file A read), concurrent write (both edit one file inside a window), shared-resource clash (two builds on one target dir, same port, git index lock), branch drift (worktree base moved).
- In look mode, conflicts are recorded as would-have notices. In optimize mode, they are injected into the affected session at its next hook.

**L2. Shared learning (passive, automatic, rare).**
- A per-machine signature memory: failure signature → how it ended (fixed by which edit, in which session, how long it took).
- Delivered only when it pays: a session hits a known signature a second time, or a loop starts on it.
- Guard overrides and shape levels already persist per project (E9). Fleet makes them visible to concurrent sessions, not only to later ones.
- Notes: an agent or user posts `tend note "integration tests need DB_URL"`. Notes from agents wait in a review queue. The user promotes them. Promoted notes go to new sessions on that project at SessionStart.

**L3. Messaging (explicit, agent-initiated).**
- Agents send with a shell command (`tend msg <to> "…"`), so it works for any agent that has a shell, across providers. An MCP surface comes later (E13).
- Addressing: a session id, a name the user gives (`--tend-name reviewer`), a role (`@workers`), or a topic (`#api`).
- Delivery happens at the receiver's next hook point, as added context. It never edits the past. A message is never delivered in the middle of a tool result.
- Inbox: `tend inbox` for the agent and the user. Unread count in `tend status`.

**L4. Coordination (topologies).**
- The user picks a topology in a fleet file (`.tend/fleet.toml` or a flag). Presets:
  - `solo`: default. L1 and L2 only, no messages.
  - `peers`: everyone can message everyone. Shared claims on files and tasks.
  - `lead`: one leader, N workers. Workers receive tasks only from the leader and report only to it. The leader sees all worker state.
  - `pipeline`: A's Stop sends A's summary and diff to B, and so on.
  - `custom`: roles plus a table of who may send what to whom.
- Primitives the topologies are built from:
  - **Claims (leases).** "I am editing `src/api/*` for 20 min." Others get a notice or (optimize, opt-in) a deny on a conflicting edit. Leases expire, so a dead session never holds a lock.
  - **Task board.** post, claim, done, blocked. With `depends_on`.
  - **Handoff.** On Stop: summary, diff ref, open failures, sent to the next role.
  - **Wake.** A worker that finished can be kept going by its Stop hook with the next task (`continue_turn`). A session idle at the prompt cannot be woken by hooks; the user sees the unread count instead.
- tend is the substrate: bus, ledger, policy, delivery. The leader's brain is an agent session, not tend. tend does not plan work.

**Fleet management (core, cuts across layers).**
- `tend fleet spawn --agent claude [--worktree <branch>] [--repo <dir>] --task "<prompt>"` starts a headless session under tend. With `--worktree` it creates the worktree first. The spawned session joins the fleet like any other, and it is tagged with its parent.
- Lifecycle: `tend fleet` lists live and finished sessions. `tend fleet stop <id>|--all` stops them (the same signal path as S7). `tend fleet logs <id>` shows a session's report.
- Results: on exit, the worker's last message, diff ref, audit line (E2), and open failures go to the spawner's inbox (the user or a parent session).
- Limits, set in config and enforced by tend: maximum concurrent sessions, maximum wall time per session, and a fleet-wide token budget from transcript usage. When a limit is hit, tend stops new spawns and tells the user. It never kills work silently.
- Permissions: a spawned session gets the permission mode the user names on the command, or the default. A parent session can never spawn a child with a looser mode than its own.
- Interactive sessions are not spawned in a terminal (tend is not a multiplexer). For one, tend prints the command to run.
- Cleanup: `tend fleet prune` removes finished worktrees that have no unmerged commits, after a confirmation.

**Awareness across setups.**

| Setup | What awareness covers |
|---|---|
| Same checkout | Stale reads, concurrent writes, git index lock, two builds on one target dir. |
| Git worktrees | The same, matched by repo-relative path across worktrees (the merge will collide). Plus base drift: another worktree merged into the base branch. |
| Different repos | Shared resources (ports, global caches, the GPU, one usage limit), the fleet view, and learning from toolchain-level signatures (for example, the same rustc or pip error). |

### 1.3 What it must not become

- Not a chat app between agents. Messages are short, typed, rate-limited, and recorded.
- Not a planner. tend spawns, connects, and limits sessions, but it does not decide what work to do, and the core calls no model (core rule 2, principle 7).
- Not a terminal multiplexer (out of scope in the reference, §4).
- Not a network service. One machine, one user, Unix sockets, 0700 dirs.

## 2. How the tend rules shape it

| Rule | Consequence for fleet |
|---|---|
| 1. Fail open | If the fleet hub is down or slow, every session behaves as a solo session. A hook never waits on another session. |
| 2. Core has no I/O | Fleet logic (conflicts, routing, lease expiry, topology permissions) is a pure function over events from many sessions, in `tend-core/src/fleet.rs`. Time comes in as `now_ms`. |
| 3. Never edit the past | Deliveries are added context at the next hook. Nothing already seen is changed. |
| 4. Every action recorded | Each delivery is an action in the receiver's ledger, with a cause that points to the sender's entry (`session:seq`). `tend why` follows the link across ledgers. |
| 5. Look mode returns nothing | In look mode, fleet records "would have told B …" and shows it in the report. Nothing is injected. |
| 6. Deterministic | Session order, routing, and output are sorted by id, never by HashMap order. |
| 7. Shim stays thin | The shim talks only to its own session daemon, as today. The daemon talks to the hub off the hot path; the inbox is read from local memory. |
| 8. Capability-honest | Delivery plans with `inject_context`, `continue_turn`, `deny`. A peer that cannot receive is marked "read-only" in the fleet view. |

## 3. Risks

| Risk | Effect | Mitigation |
|---|---|---|
| Prompt injection spreads | Session A reads a poisoned web page. It messages B, which has more permissions. The fleet becomes a worm. | Messages are labeled untrusted data with provenance. A message can never grant a permission, lift a block, or run `tend allow`. Rate limit per sender. Topology limits who may send. Agent notes need user promotion. |
| Context noise and cost | Every delivery costs tokens and stays in the transcript. | Deliver at most N per turn. Conflicts first. Learning only on a second hit or a loop. Digest many messages into one. |
| False conflicts | Users turn it off. | Look mode first. Measure the false-notice rate from flags, as with the guard. |
| Scope creep | The owner overrode the 2026-10-20 feature gate for fleet. | F1 starts with a measurement from existing transcripts. Each phase after F1 has its own gate. |
| Runaway spawns | A parent spawns children that spawn more. Cost and load grow without bound. | A depth limit (default 1: children cannot spawn), a concurrency limit, a token budget, and `tend fleet stop --all`. Every spawn is a ledger action with its reason. |
| Worktree clutter | Spawned worktrees pile up. | Spawned worktrees go under one tend-owned directory. `prune` lists them and asks before it removes any. |
| Cross-provider is not yet real | Codex is blocked on S10 (no Codex CLI). | Design over the common event vocabulary. Ship Claude Code ↔ Claude Code first. |
| Lead and wake depend on unverified agent behavior | Stop continuation may loop or be capped. | Mark `[Verify]`. Spike before building L4. |

## 4. Plan

Each phase has an exit gate. The next phase starts only if the gate passes.

### F1. Awareness (L1), build now

First step, F1.0 (does not block): measure from `~/.claude/projects` transcripts.
- How often were two or more sessions live at once, on one checkout, on worktrees of one repo, and on different repos?
- How often did they touch the same repo-relative file within 10 minutes?
- How often did two sessions hit the same error signature?
- Reuse `retro.rs` (`--all`) and `perception/signature.rs`.
- Write the table to `docs/fleet-2026-10-21.md`. It also gives the rules their first real fixtures.

Then:
- Hub process: `tendd-hub`, one per user, started lazily by the first session daemon, exits when the last one leaves. Socket in `<tmp>/tend-<uid>/hub.sock`, 0700.
- Session daemons publish a small event digest (tool, paths read and written, command kind, signature, state) to the hub. They subscribe to notices for themselves.
- `tend-core/src/fleet.rs`: pure `FleetModel` and `fleet::handle(events, now_ms) -> Vec<Notice>`. Conflict rules: stale read, concurrent write, resource clash.
- New ledger kinds (additive, format stays 1): `fleet_peer`, `fleet_notice`. Cross-ledger causes as `{session, seq}`.
- CLI: `tend fleet` (live view), fleet section in `tend report`.
- Look mode only at first.
- **Gate:** a week of real use; notices are correct (flags reviewed).

### F2. Shared learning (L2)
- Signature memory in `<home>/fleet/signatures.jsonl`: signature, project, outcome, fix diff ref, session.
- Delivery rule: a second hit or a loop start.
- `tend note`, review queue, promotion (`tend notes --promote`).
- **Gate:** at least one real hit where the delivered fix was the right one.

### F3. Fleet management (spawn and lifecycle)
- See `docs/fleet-topologies-2026-10-21.md` §8 (F-S1, F-S2, F3a, F3b).

### F4. Messaging (L3)
- `tend msg`, `tend inbox`, names and roles (`--tend-name`, `--tend-role`).
- Delivery at UserPromptSubmit, PostToolUse, and SessionStart through `inject_context`. Digest and rate limits.
- PreToolUse denies the agent's own attempts to forge sender or escalate (the same pattern as `tend allow` in S6).
- Optimize mode only.

### F5. Coordination (L4)
- See `docs/fleet-topologies-2026-10-21.md` §8 (F5a–F5g): task board, check gate, claims, budgets, reports, presets.

### F6. Cross-provider
- After the Codex connector (S10, E12). Fleet already works over common events, so this is a connector task, not a fleet task.

## 7. Measurement (F1.0, 2026-10-21)

Run: `scripts/fleet_measure.py` over `~/.claude/projects`. Active time is a session's messages with gaps over 10 min removed. Sessions under `/tmp` are bench and conformance runs; they are counted apart.

| Question | Real sessions (7, over 4 active days) | Synthetic (182, /tmp) |
|---|---|---|
| Days with concurrent sessions | 1 | 1 |
| Concurrent pairs, same checkout | 0 | 0 |
| Concurrent pairs, worktrees of one repo | 0 | 0 |
| Concurrent pairs, different repos | 3 (31 min overlap) | 187 (bench, `--parallel`) |
| Same repo file written by a concurrent pair within 10 min | 0 | 0 |
| Error signatures in 2+ sessions | 2 of 39: a generic `Traceback` line, and `gpg failed to sign the data` | 8 of 17, mostly repeated bench setup |

**Reading:**
- **The data is too small to judge collisions.** Only 7 real transcripts are left (Claude Code removes old ones). They show no same-checkout or worktree overlap, so the stale-read and concurrent-write rules have no real case yet.
- **Concurrent work on different repos does happen.** That is the fleet view and resource-clash case.
- **One real learning case.** `gpg failed to sign the data` hit two sessions on different repos. That is a machine-level fix, which a second session could have been told about. It argues for toolchain-level signatures in F2, not only per-project ones.
- **A false collision, found and fixed.** A resumed session copies the earlier messages into a new transcript. The first run read the copy as a second agent writing the same files at the same seconds. The script now counts each message uuid once. The live hub sees only live daemons, so it cannot make this mistake, but any retro-based fleet view must dedupe the same way.
- **Consequence for F1.** Build it as decided. The first real fixtures for the collision rules must come from a deliberate two-session run (the live check in §6), because history has none.
